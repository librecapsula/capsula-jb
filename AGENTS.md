# AGENTS.md — инструкция для LLM-агентов: разработка

Инструкция по прошивке колонки для конечного пользователя — отдельный
файл `resources/packaging/AGENTS.md`; он же кладётся в релизные
архивы. Этот файл — о работе над репозиторием.

## Сборка и тесты

- `cargo build --release` — нужен Rust и C-компилятор (lwext4
  собирается через `cc`, см. `jb-rockchip/build.rs`). Версия Rust не
  запинена: CI использует предустановленный на раннерах stable
  (докачивает только компоненты clippy/rustfmt и кросс-таргеты),
  локально — default-тулчейн rustup; edition — 2024 (задаётся в
  `[workspace.package]`, крейты наследуют).
- `cargo test --workspace` — тесты userdata гоняют настоящий lwext4 на
  синтетических образах и сериализованы общим мьютексом (у lwext4
  глобальное состояние); тесты UBIFS-сборки образа data — на
  синтетических захватках через крейт `ubifs`; протокольные тесты
  работают на MockTransport, без железа и без сети.
- Подписанный лоадер (`resources/loader/loader.bin`, из OTA Capsule-14
  44.90) — единственный бинарник прошивки в репозитории (хранение
  разрешено); вшивается в бинарник jb-rockchip и проверяется обычным
  тестом (`jb_rockchip::loader`). Сеть инструмент не использует:
  скачивания OTA с VK CDN больше нет (модули `ota`/`rkfw` удалены).

## Архитектура: крейты и сценарий

Три слоя, стрелка = «зависит от»:

```
jb-cli → jb-tui → jb-core ← jb-rockchip / jb-amlogic
```

- **jb-core** — контракт и общий домен, без USB-транспорта и UI:
  `backend` (трейт платформы: `present` / `wait_hint` / `connect` —
  идентичность без дампа и записей — / `platform` — доступ к хукам),
  `model` (единый реестр моделей колонок: `Model::ALL` — порядок меню
  TUI и скана каталога, `label()` — подпись, `name()` — каноническое
  имя, оно же значение `--model`, сегмент `backup/<name>/` и serde-имя
  в `backup.json`, `from_name()`/`names()` — парсинг и словарь для
  сообщений; новое место, где перечисляются колонки, — только здесь),
  `session` (событийная модель: воркер-нить владеет бэкендами,
  команды `Command::{Jailbreak,Backup,Restore}` и события
  `Event::{WaitingForDevice,Connecting,DeviceConnected,BackupState,
  Progress,ConfirmRequested,AttentionRequested,Finished}` —
  `Connecting` = устройство найдено, идёт bring-up;
  `AttentionRequested` = раунд-трип «продолжить без полного бэкапа?»
  (rockchip: деградированный флоу), закрытый канал = «прервано»;
  confirm — тот же раунд-трип через канал), `scenario` (скелет джейлбрейка:
  ensure_backup → data_size → confirm → build_data_image →
  write_data_image → finish; трейт `Platform` — платформенные хуки
  `ensure_backup`/`backup_state`/…, типы `Params`/`Prepared`/
  `WritePlan`/`BackupState`), `progress` (события для UI), `overlay`
  (набор оверлей-файлов: adbd (отключается `--no-adbd`/тумблером) +
  флаг гаджета + маркер — одинаков для обеих платформ),
  `backup_catalog` (единый манифест бэкапов v2 `backup.json`,
  публикация/чтение/верификация/каталог), `backup_store` (низкоуровневые
  помощники: имена, sha256, CaptureDirectory для amlogic-чекпоинтов),
  `config` (в т.ч. хинты подключения `hint.connect_text` по
  каноническому имени модели), `format`.
- **jb-rockchip** (RK3308) — домен: bring-up по персонам rockusb
  (`session`: `bring_up` с целью `Goal::{StockLoader,UsbPlug}` —
  продакшен-connect идёт с `Goal::UsbPlug`: серийник с 330d → сброс в
  MaskROM → выгрузка usbplug в RAM (окно ожидания персоны — 10 с);
  колонка, которая не запускает наш лоадер, возвращается как
  `BringUpError::FirstGeneration { serial }` (серийник-эвристика
  первого поколения ИЛИ несовместимая партия 0100), платформа
  переводит себя в `Prep::StockOnly` и отдаёт `ConnectError::Attention`
  — после «Продолжить» принимается ТОЛЬКО персона 330d той же колонки;
  `Goal::StockLoader` — деградированный реконнект и --no-backup;
  `reattach` — повторное подключение известной колонки из любой
  персоны для ретраев), GPT (`gpt`),
  полный дамп (`backup` — суммы стримятся при дампе, отчёт несёт
  `ImageEntry` для запечатывания v2; на стоковом лоадере срез — по
  boot_a НЕ включая: от boot_a и всё, что выходит за 32-МиБ маску
  чтения, ПРОПУСКАЕТСЯ — `skipped`-список
  вместо мусорных образов), ext4-оверлей через lwext4
  (`userdata`), запись WRITE_LBA (`flash`), вшитый лоадер
  (`loader`), первое поколение (`firstgen`); в `platform` — реализация
  `Backend`+`Platform` (включая супервизор win-drv и запечатывание
  `seal_backup`).
- **jb-amlogic** (A113X) — домен: окружение u-boot (`env`),
  чекпоинт-захват NAND (`capture` — schema-2 `manifest.json` остаётся
  форматом чекпоинтов; по завершении публикуется единый v2
  `publish_v2`, директории, завершённые старыми версиями, публикуют
  v2 лениво при первом открытии), UBIFS-сборка образа data
  (`data_image`), оконная запись (`write`), пасстру-диагностика
  (`diag`); в `platform` — реализация `Backend`+`Platform`
  (connect = ловля окна + съём окружения → deviceid).
- **jb-cli** — только бинарник: аргументы, фабрика платформ
  (`backend::for_model`; модель указывается ДО старта сессии — в CLI
  обязательный для сценариевых команд `--model capsula |
  capsula-mini-amlogic` (значение типизировано реестром
  `Model::ALL`, возможные значения показывает clap), в
  TUI — меню; воркер сессии получает бэкенд одной выбранной модели и
  опрашивает шину только через её `Backend::present` — колонка другой
  платформы на шине не видна в принципе), цикл событий сессии для CLI
  (Progress → indicatif-бары, ConfirmRequested → консольный
  «запись/восстановление …: продолжить? [y/N]» — формулировка
  приходит из `WritePlan` платформы; AttentionRequested → notice в
  лог + «продолжить без полного бэкапа? [y/N]»), монитор шины.
  Глобальные флаги
  (`--yes`/`--wait`/...) — `global = true`, работают до и после
  подкоманды. Офлайн-подкоманды (без устройства и сессии):
  `backups [--verify]` — листинг каталога (CLI-двойник панели бэкапов
  TUI), `backup-delete <model> <key>` — удаление с тем же [y/N]
  подтверждением; каждое действие TUI имеет CLI-эквивалент.
- **jb-tui** — терминальный UI (ratatui + crossterm, чистый Rust —
  все три ОС, включая кросс-сборку aarch64-linux в CI): открывается
  при запуске **без единого аргумента И в интерактивном терминале**
  (оба — stdin и stdout — tty; ветка в `main()` jb-cli ДО
  `Cli::parse` и ДО инициализации CLI-логгера — TUI ставит свой
  мост `log`-→панель). Любой аргумент ИЛИ пайп/редирект вместо
  терминала (агенты, CI) оставляет CLI-путь — агент никогда не
  попадает в TUI, безаргументный запуск отдаёт ему обычный
  CLI-сценарий с подтверждением. Экраны:
  выбор модели (меню: стрелки/Enter, клик; смена модели = полный
  перезапуск инструмента; воркер сессии стартует только здесь, с
  бэкендом выбранной модели) → ожидание колонки (инструкции
  подключения из `config`-хинтов — показываются только здесь, после
  выбора; Esc/q — выход) → «подготавливаем колонку» (по событию
  `Connecting`: устройство найдено, идёт bring-up — выгрузка лоадера,
  драйверы; без контролов, живой лог) →
  рабочий экран (инфо о колонке + first-gen
  варнинг, панель бэкапов: снять/восстановить/удалить, настройки:
  adbd/форматировать/без бэкапа, лог, прогресс, «ПРОШИТЬ»). Между
  ожиданием и рабочим экраном может встать модал первого поколения
  (`AttentionRequested`: одна кнопка «Продолжить», Esc = прервать
  запуск; за ним — экран ожидания, принимающий только 330d). Всё
  управляется и с клавиатуры (Tab/стрелки/Enter/Space, Esc/q), и
  мышью (клик = фокус + активация, колесо — скролл лога); во время
  операции выход заблокирован (запись нельзя прерывать). Стейт-машина
  и рендер тестируются без терминала (TestBackend + FakeBackend).

## Подкоманды сценария

Соединение (`Backend::connect`: bring-up + идентичность — серийник или
deviceid, firstgen-флаг) делает воркер сессии до всяких команд; перед
connect воркер эмитит `Event::Connecting` (TUI показывает экран
«подготавливаем колонку», CLI — строку в лог). Ошибка connect
типизирована (`ConnectError`): `Fatal` убивает запуск, `Attention` —
«продолжить без полного бэкапа?» (rockchip, см. «Первое поколение»):
notice уходит в UI (TUI-модал с одной кнопкой «Продолжить», CLI —
[y/N]), после Proceed воркер снова ждёт устройство (бэкенд сам сужает
`present()` до принятой персоны) и коннектится повторно; Abort/закрытый
канал = «прервано пользователем». Операции идут по подключённому
`Platform`:

- `jailbreak` — ensure_backup (верифицированный бэкап есть → пропуск
  дампа; нет → захват + запечатывание v2) → замер data → confirm →
  сборка образа с оверлеем (fsck-fallback на битом захвате) → запись →
  finish;
- `backup` — ensure_backup (захват, на колонку не пишется) → отчёт
  платформы;
- `restore` — **полное восстановление**: ensure_backup → `restore_set`
  (верифицированный захват обязателен; в набор идут ТОЛЬКО целые
  образы — нецелые (маска 0xCC первого поколения, бед-блоки amlogic)
  перечисляются в пропусках и никогда не прошиваются) → confirm (план:
  «все разделы», суммарный размер, пропуски в описании) →
  `write_restore` → finish. Rockchip пишет каждый образ в его раздел
  по ЖИВОЙ GPT (не влезает — ошибка), в конце — саму GPT (LBA 1) и
  idblock (LBA 0x40). Amlogic пишет разделы по карте (bootloader →
  data, оконная запись с полным физическим erase каждого); AML-reserved
  и окружение device-уникальны и НЕ прошиваются никогда. Это откат
  всего, что делалось после захвата: оверлей джейлбрейка, записи и
  изменения разделов затираются, содержимое захвата возвращается.
  `--no-backup` и `--format-userdata` с подкомандой несовместимы и
  отвергаются.

Новая платформа = новый крейт `jb-<имя>` с реализацией `Backend` (и
`Platform` на том же типе) + ветка в `backend::for_model`;
существующие платформы при этом не трогаются. После записи ничего не
верифицируется ни на одной платформе (запись — последнее касание
устройства) — поведение rockchip-флоу сохранено и для amlogic.

Весь вывод инструмента — через фасад `log`. CLI: единый логгер
(`jb-cli/src/logging.rs`): формат `HH:MM:SS.mmm LEVEL  сообщение`
(UTC, stdout, уровень — RUST_LOG, по умолчанию info); логи доменных
крейтов (rockusb/amlogic/jb-core/jb-rockchip/jb-amlogic) попадают туда
же. TUI ставит свой мост (`jb-tui/src/logger.rs`) с тем же форматом в
панель лога (после выхода записи падают в stderr). Новые сообщения —
только log-макросами (`info!`/`warn!`), не println: прямой print идёт
без метки времени. Активную progress-полосу CLI-логгер на время записи
строки приостанавливает (`progress::active_bar` + suspend), чтобы
предупреждения посреди передачи не затирались её отрисовкой.

## Первое поколение (подарочные колонки) и партия 0100

Колонки первого поколения определяются по серийнику стокового u-boot
(`jb_rockchip::firstgen`: первые 4 знака не цифры — первое поколение).
Их BootROM залочен и отклоняет наш usbplug, поэтому полного (целостного)
бэкапа на них нет. То же верно для части колонок партии 0100 с обычным
серийником: если колонка вошла в MaskROM (кабель в порядке), но
переход maskrom → loader не произошёл — лоадер несовместим с этой
колонкой и НЕ поднимется (повторы бессмысленны); оба случая —
«деградированный флоу».

Флоу подключения (единый для CLI и TUI): connect сразу идёт с
`Goal::UsbPlug` — серийник с 330d, сброс в MaskROM, выгрузка usbplug
(персона ждётся до 10 с; transfer-reset на download — то же «отклонено»).
Колонка первого поколения по серийнику вовсе не сбрасывается в MaskROM.
Любой «не поднимается» → `BringUpError::FirstGeneration { serial }` →
платформа переходит в `Prep::StockOnly` и отдаёт
`ConnectError::Attention`: TUI — модал с одной кнопкой
«Продолжить» за экраном ожидания, CLI — [y/N]. Текст notice зависит от
причины: firstgen по серийнику — колонку НЕ сбрасывали, она уже в
режиме лоадера («просто нажмите „Продолжить“», перезагрузку не
просим); сброс был, лоадер не поднялся — колонка осталась в MaskROM,
просим выключить/Recovery/включить и нажать «Продолжить». После
«Продолжить» принимается ТОЛЬКО персона 330d той же колонки (другой
серийник — честный новый полный флоу для новой колонки); «Продолжить»
действует до перезапуска инструмента, тихих повторов usbplug нет.
Далее сценарий
идёт через **стоковый rockusb-лоадер** (`2207:330d`): GPT читается с
LBA1, запись userdata — штатный WRITE_LBA; `Platform`-хуки jb-rockchip
выбирают источник образа по флагу (без базы — сборка с нуля);
`attach_stock_loader` — в `session.rs`. Замерено на живом железе
(log/firstgen-stock-loader-diag-*.txt):

- стоковый лоадер отвечает chip_info («8033»), flash_detect (218 MiB
  NAND) и читает GPT целиком — таблица совпадает с Capsule-14,
  userdata 166 463 секторов на LBA 280 992;
- у стокового лоадера ЕСТЬ та же маска чтения 0xCC: всё выше LBA 0x10000
  (32 МиБ) читается как 0xCC — включая содержимое userdata (его ext2-
  суперблок виден как 0xcccc). Целостный бэкап через стоковый лоадер
  невозможен; читаемы только разделы ниже 32 МиБ (uboot, trust, misc,
  boot_a, начало boot_b);
- Read-only диагностика такой колонки:
  `cargo run -p jb-rockchip --example stock_diag --release`.

Бэкап в деградированном флоу — **частичный**: `backup::backup()` с
флагом `stock_loader = true` (без RAM-патча и 0xCC-guard — нужен наш
usbplug) дампит ТОЛЬКО разделы ДО boot_a, НЕ включая её (срез — по
позиции `boot_a` в GPT; на карте Capsule это uboot, trust, misc);
boot_a и всё после неё (boot_b пересекает 32-МиБ маску, userdata и
выше — целиком за ней) ПРОПУСКАЮТСЯ — мусорные 0xCC-образы не
пишутся вовсе, имена идут в `skipped`-список
отчёта, снятые образы все `complete: true`. Инструмент печатает
предупреждение «бэкап частичный»; v2-манифест публикуется со статусом
`partial` и заметкой с перечнем пропущенных, поэтому он никогда не
становится базой записи: userdata в деградированном флоу всегда
собирается с нуля. Restore из такого бэкапа честно предлагает только
снятые разделы (пропуски перечисляются в плане).

Особенности, которые нельзя ломать:

- **fastboot (18d1:d00d) не поддерживается и не детектируется**:
  стоковый u-boot впадает в этот режим только при сбое; инструмент
  устройство под чужим VID не видит и просто ждёт режим лоадера.
  Fastboot-сценарии не добавлять: измерено на живом железе —
  брошенная на полпути DATA-фаза клинит гаджет намертво, до
  передёргивания питания. Исследовательский дамп getvar этого
  состояния — `log/firstgen-fastboot-getvar-all-*.txt`.
- userdata на первом поколении всегда собирается с нуля: чистый ext2,
  `/overlay/upper` с файлами и **пустой** `/overlay/work`
  (overlayfs требует существующий пустой workdir — S23overlayfs.sh его
  не создаёт).
- Windows: пакета win-drv под 18d1:d00d нет и не нужно (fastboot не
  поддерживается; процедура пакета — resources/drivers/winusb/
  README.md, если когда-нибудь понадобится).

## ubifs

Крейт `ubifs` (публичная pure-Rust библиотека UBIFS/UBI: чтение с
journal replay, побайтовая сборка образов в стиле mkfs.ubifs/ubinize,
checker в духе fsck.ubifs, fsck-rebuild) вынесен в отдельный репозиторий
[roman901/ubifs-rs](https://github.com/roman901/ubifs-rs) и опубликован
на crates.io. Кода крейта в этом репозитории нет;
`jb-amlogic::data_image` использует его для сборки патченного образа
data — extract → инжект оверлея → mkfs → ubinize. Правила разработки и
паритета — в AGENTS.md того репозитория.

- **fsck-fallback при сборке образа**: строгий open захвата может
  отказать на повреждённом томе (после многократных отключений питания
  встречается committed-индекс, ссылающийся на unmapped/garbage LEB —
  диагноз 2026-11-01, колонки 0151/0306: стабильные «index leb N is
  unmapped» / «bad node … bad magic», захваты при этом честные). Тогда
  `data_image` уходит в `ubifs::fsck::rebuild` — точный порт
  официального rebuild-режима (`fsck.ubifs -y -b`, rebuild_fs.c):
  скан всех main-LEB без индекса и БЕЗ границы sqnum (незакоммиченный
  bud-хвост восстанавливается; master вообще не нужен), семантическая
  валидация нод как в официальных parse_*, удаления через маркеры
  nlink-0/inum-0, trun-ноды (устаревшие блоки отбрасываются, размер —
  по calculate_file_info), дыры в файлах → нули (файл НИКОГДА не
  обрезается и не выбрасывается из-за потери блока — как в оригинале),
  хардлинки сохраняются ссылками (rebuild отдаёт walk::Plan, сборка —
  mkfs_plan). Недостижимые файлы (дент не восстановился) УДАЛЯЮТСЯ —
  lost+found в официальном rebuild-режиме нет (это поведение
  non-rebuild режимов, которые чинят живой TNC на месте); нет
  корневого inode — создаётся пустая ФС (create_root). Отчёт rebuild
  печатает все потери. Восстановленный образ самопроверяется строгой
  читалкой как обычно.


## Ограничения, которые нельзя ломать

- `.cargo/config.toml` резервирует 8 МиБ стека главного потока на
  Windows-таргетах (`/STACK:8388608`) — с запасом под рекурсивные
  парсеры (исторически предел ставил рекурсивный парсинг
  OTA-манифеста, требовавший больше дефолтных для MSVC-линкера 1 МиБ).
  Конфиг не удалять и не занижать.
- `BULK_IN_MAX` в `rockusb/src/transport.rs` и его копия в
  `amlogic/src/transport.rs` (1 МиБ) — потолок одного bulk-IN запроса
  на Windows: nusb включает RAW_IO, и WinUSB не дробит RAW_IO-запросы —
  всё выше maximum transfer size хост-стека (замерено: 2 МиБ проходит,
  3 МиБ падает с `usb: unknown (error 1)`) отклоняется мгновенно.
  Проверить потолок на новом железе:
  `cargo run -p jb-rockchip --example readsize --release`.
- Файлы в `resources/drivers/winusb/` (INF+CAT+CER) — подписанные
  артефакты Zadig/libwdi: каталог подписывает ровно этот INF, поэтому
  их нельзя переименовывать и править (включая DriverVer). Новый PID =
  новый пакет против живого устройства — процедура в
  `resources/drivers/winusb/README.md`.

## Amlogic (Capsula Mini поздних ревизий, A113X)

Мини на Amlogic — второй бэкенд (крейт `jb-amlogic`), протокол —
крейт `crates/amlogic` (порт вендорского update/burning-протокола
`1b8e:c003`: identify, память, bulkcmd, media download/upload).
Транспорт — внутри крейта, отдельного usbcore НЕТ и заведомо не делать:
amlogic нужны пер-запросные таймауты control-передач, short bulk-чтения
с сохранением префикса, наблюдаемые ZLP и port reset — семантика,
которой у rockchip-транспорта нет. Формат провода, таймауты и строки
статуса — по реверс-инжиниринг-спецификации «Amlogic A113X USB
Protocol Specification» (AML-A113X-USB-1.0), pyamlboot и дизасму
вендорского update (1.5 — тот, что ходит в flasher.sh, и 1.7.5 —
пересборка в `../tools/update-macos`); media-голова и флоу записи —
байт-в-байт по тулу 1.5, проверенному на этой плате.

- Download-окно: стоковый u-boot поднимает `1b8e:c003` при каждом
  включении; identify принимается ~450 мс (`identifyWaitTime=450`).
  Ловится горячим циклом open+identify+prime (`bring_up` в бэкенде):
  «нет устройства» = пустая шина, до 10 подряд неудачных open/identify
  = устойчивая проблема (обычно драйвер). identify шлётся немедленно,
  первый bulkcmd сессии — жертвенный `echo` (prime); стадия обязана
  быть TPL (u-boot burning gadget) — BootROM мини залочен паролем и
  для сценария бесполезен. **Тёплый цикл гаджет не поднимает**
  (проверено на живой плате: `run try_auto_burn`, port reset,
  правки bootcmd — переэнумерации нет), окно = холодное включение.
- Сессия после установления контакта живёт, ПОКА идёт работа: смерть
  наступает на простое (~300–450 мс без device-side активности).
  identify-keepalive между операциями сбрасывает таймер (замер
  2026-10-31: сессия вывозит 20 × 8 МиБ подряд, ~11.7 МБ/с, полный
  захват NAND — одна сессия ~1 мин). Чтение — механика flasher.sh
  `read_big_from_flash` (`amlogic::nand::read_nand_range`, этапы по 8
  МиБ главных, raw — по 4 МиБ): identify → `mw.b` сентинель → один
  blocking `nand read` (статус-чтение абсорбирует молчание стейджинга)
  → один `upload mem` → стрим в writer по этапам. Смерть сессии
  сохраняет префикс этапов на диске — чекпоинт.
- Полный захват — чекпоинт-цикл (`jb_amlogic::capture`: `open_or_start`
  + повтор `capture_pass`; бюджетов нет — проход длится до конца или до
  смерти сессии): окружение u-boot, **таблица разделов с устройства**
  (`imgread dtb <slot>` + строгий парсер `amlogic::fdt`; на Mini нет
  GPT — DTB boot-образа и есть таблица; карта сверяется с известной
  `amlogic::PARTITIONS`, чужая плата отвергается), разделы по
  логической ёмкости (`store size`, бед-блоки исключены), AML-reserved
  области. **Сырого дампа NAND нет** — ничто его не потребляет
  (восстановление пишет только data, база — data), а время и размер
  захвата он удваивает. Каталог бэкапа повторяет структуру rockchip:
  нумерованные образы `NN_<имя>.img` по порядку карты (01_bootloader,
  02_tpl, …, 08_data), `device.dtb` (аналог `.gpt.bin`), человекочитаемая
  `partition_table.tsv` того же формата, что GPT-вывод rockchip (idx,
  name, first LBA, sectors — смещения кратны странице, единицы
  точные), плюс env.txt/env-export.bin и reserved-области; в
  `backup/capsule-mini/<deviceid>/` (раскладка v2, см. «Бэкапы:
  раскладка v2 и каталог»). Внутри `manifest.json` (schema 2: разметка
  + reserved + контрольные суммы; verify перепроверяет разметку по
  device.dtb) как формат чекпоинтов и единый `backup.json` v2,
  публикуемый по завершении (`publish_v2`); чекпоинт = манифест +
  `.partial`-файлы, переживает и смерти сессий, и перезапуски инструмента.
  Старые каталоги (файлы `<имя>.bin`, сырой NAND) отвергаются с
  просьбой удалить и переснять — миграции нет. Слоты DTB: `boot_part`
  из окружения, потом boot_a/boot_b. Три сессии подряд без прироста
  байт — ошибка (кабель/драйвер).
- Media-голова (download-путь): **индекс чанка на 0x08, сумма на
  0x0c** — порядок подтверждён на проводе (2026-10-31: перепутанный
  порядок отвергается гаджетом с диагностикой «genSum … != org … at
  seq …»); алгоритм `0xef` + ack-длина `0x100` на 0x10. Media-стрим
  живёт не дольше ~300 мс (4 МиБ проходит, 8 МиБ умирают) — куски
  записи 2 МиБ.
- Образ data: раздел — **UBI с одним UBIFS-томом `data`** (overlayfs
  upper — `/data/overlay/upper`, work — `/data/overlay/work`, та же
  схема, что на rockchip). Оверлей накладывается перепаковкой ФС
  (`jb_amlogic::data_image`, крейт `ubifs` с crates.io): захват
  открывается с journal replay, дерево извлекается, overlay-файлы
  инжектируются, ФС собирается заново с параметрами стока (fmt 4,
  min_io 2048, LEB 126976, max_leb_cnt 2212, lzo, jheads 1, log 5,
  orph 1 — снимаются с суперблока захвата, для fresh — константы
  профиля), том — dynamic+autoresize (ядро расширяет ФС на весь
  раздел при первом attach: `fs/ubifs/super.c`: `c->leb_cnt =
  c->vi.size`; суперблок при монтировании игнорируется), хвост добивается
  пустыми PEB (EC+0xFF, EC-счётчики продолжаются за захват) ровно до
  ёмкости `store size` на момент записи. Образ самопроверяется
  перечитыванием до записи (lookup + байты + права каждого
  overlay-файла); после записи — никакой верификации (паритет с
  rockchip).
- Запись: разделы пишутся как во flasher.sh, кусками между сессиями
  (`Amlogic::write_partition_windowed` над `jb_amlogic::write::
  write_data_pass` + `amlogic::store::write_nand_chunk`) — и образ
  data джейлбрейка, и каждый раздел полного восстановления: на каждый
  кусок 1 МиБ — identify-keepalive, `download mem` в ОЗУ (arm через
  TPL-канал), media-пакеты, `download get_status`, `nand write` по
  логическому смещению (u-boot сам обходит бед-блоки). Смерть сессии
  посреди `nand write` (или между разделами) — следующий проход
  ПОВТОРЯЕТ полный erase и пишет с нуля (запись занимает одну сессию
  ~13 с, повтор дёшев). Состояние между сессиями — `WriteState`
  (записано + нужен ли erase). Media-флоу и дедлайны — как у
  вендорского тула (ack 12 мин/попытка, статус bulkcmd 20 мин, пустой
  ответ статуса перечитывается).
- **Арифметика erase/write НЕ совпадает — не сломать** (диагноз
  factory-режима 2026-11-01, log/aml-flash-*-factory-diag-*.txt): в
  этом u-boot `nand write`/`nand read` считают длину по ЛОГИЧЕСКОМУ
  пространству (skip-bad), а `nand erase` — по ФИЗИЧЕСКОМУ диапазону
  (бед-блоки пропускаются по ходу, но длина не растягивается). В data
  два бед-блока (0xc000000, 0xc020000), поэтому erase «на размер
  образа» стирал на 2 PEB меньше хвоста, чем записывал write: хвост
  перезаписывался поверх нестёртого/оставался со старым EC — UBI
  отвергал весь раздел («bad image sequence number … in PEB …»), а
  стоковая система переформатировала data («UBIFS: default file-system
  created») и уходила в factory. Поэтому `write_data_pass` стирает
  ВСЕГДА весь физический диапазон раздела (physical size из карты
  разделов): после записи каждый PEB либо наш, либо чистый 0xFF
  (free для UBI).
- Путь записи ПРОВЕРЕН на живом железе (2026-11-01): чистый attach
  mtd7 с первого раза, единый image_seq, том `data` авторасширен
  15→579 LEB, UBIFS смонтирован с UUID стокового захвата (контент
  патченного образа), voice-agent стартовал, adbd поднялся. Открытое
  наблюдение (не блокер): при первом attach UBI ругается «volume
  table copy #1 is corrupted» и восстанавливает таблицу из копии #0 —
  причина побитой второй копии vtbl (LEB 1) под вопросом; UBI сам
  чинит.
- AML-reserved-области (bbt/env/keys/dtbrsv/ddr) device-уникальны и из
  дампа НЕ прошиваются.
- Example `cargo run -p jb-amlogic --example aml --release -- "<cmd>"`
  — пасстру burning-команд (диагностика, не пользовательская
  подкоманда; `upload mem <addr> normal <size>` печатает hexdump,
  `sleep <ms>` — хостовая пауза, `id` — одиночный
  identify-keepalive, `readtest <n> <size>` — мерить пропускную
  способность сессии, `dlmem <size>` — media-флоу до DRAM со
  сверкой).
- Windows: WinUSB-пакета под `1b8e:c003` нет (новый PID = генерация
  пакета против живого устройства, процедура в
  `resources/drivers/winusb/README.md`) — привязка вручную через Zadig,
  win-drv об amlogic-устройствах не ведает.

## win-drv (Windows-драйверы)

Крейт `crates/win-drv` держит плату на WinUSB без ручного Zadig: пакеты
зашиты в бинарник, сертификаты ставятся в **машинные**
Root/TrustedPublisher (`CertOpenStore(CERT_SYSTEM_STORE_LOCAL_MACHINE)`;
`CertOpenSystemStore` здесь ошибка — он пишет в хранилища текущего
пользователя и вешает процесс на модальном диалоге Windows), привязка —
`UpdateDriverForPlugAndPlayDevices` с FORCE (тот же newdev API, что у
Zadig), сессия следит за шиной и перевязывает узлы, перехваченные
вендорским Rockusb. Повышение — манифестом requireAdministrator,
вшитым ресурсом через `embed-resource` в jb-cli (путь через
`/MANIFESTUAC` в rustflags не работает — link.exe не принимает его в
этой форме). Живой тест: удалить libwdi-пакеты (`pnputil
/delete-driver oemNN.inf /uninstall /force`) и сертификаты (`certutil
-delstore Root/TrustedPublisher <thumbprint>`), запустить
`capsula-jb backup` из непривилегированного контекста — сценарий должен
сам дойти до «reading GPT» и полного дампа.

## Бэкапы: раскладка v2 и каталог

Бэкапы лежат по моделям: `backup/<модель>/<ключ>/` (`backup/capsule/
<серийник>/` на rockchip, `backup/capsule-mini/<deviceid>/` на
amlogic) — серийник rockchip и deviceid amlogic теоретически могут
совпасть, поэтому раскладка пос_MODELная. Ключ читается **ровно один
раз** — при `connect` (rockchip: распознавание персоны лоадера 330d,
u-boot chipid, тот же номер, что System Profiler; остальные персоны
его не перечитывают — BootROM-гаджет рапортует нули; amlogic:
`deviceid` из окружения u-boot, окружение читается один раз за запуск
и сразу пишется в захват, так что докачка после перезапуска инстру
продолжает тот же каталог, а подмена каталога с чужим окружением
отвергается).

Единый манифест завершённого бэкапа — **`backup.json` (формат v2)**:
модель, ключ, дата, статус `complete|partial` (+заметки: 0xCС первого
поколения, бед-блоки), образы разделов с sha256/размером/признаком
целостности, метаданные (rockchip: gpt/таблица/serial/idblock —
idblock это таблица загрузочных образов BootROM на LBA 0x40, вне
GPT-разделов, читается отдельным READ_LBA на обеих персонах; amlogic:
env/dtb/таблица/reserved).
Публикация атомарна (tmp+rename) и является ПОСЛЕДНИМ шагом захвата:
пока `backup.json` нет — бэкапа нет. Суммы rockchip стримятся прямо
при дампе; amlogic конвертирует свой schema-2 `manifest.json` (он
остаётся форматом чекпоинтов) без перехеширования (`publish_v2`).
Чтение/верификация/каталог — `jb_core::backup_catalog`
(`read`/`open`/`scan`/`BackupEntry::verify`); верификация — полный
проход SHA256, гейт перед тем, как захват станет базой единственной
копии. Старые (до-v2) каталоги НЕ читаются и НЕ мигрируются — бэкап
проще переснять: инструмент не видит бэкапа и дампит заново в тот же
каталог, публикуя v2 поверх. Если каталог с верифицированным v2-бэкапом
уже есть, дамп пропускается и сценарий сразу идёт к записи userdata.
Нюансы:

- в деградированном флоу (первое поколение / партия 0100 — см.
  «Первое поколение») дамп **частичный**: снимаются только разделы
  ниже 32-МиБ маски, публикуется со статусом `partial` и заметками с
  перечнем пропущенных; базой не подлежит, восстановить можно только
  снятые разделы; проверить бэкап без железа —
  `cargo run -p jb-rockchip --example store_check --release -- backup/capsula/<серийник>`
  (в релизном бинарнике то же — `capsula-jb backups --verify`);
- `--no-backup` (CLI; в TUI — тумблер «без бэкапа») пропускает и
  проверку, и съём дампа: образ data всегда собирается с нуля
  (rockchip — чистый ext2, amlogic — чистый ubifs), каталог `backup/`
  не читается вовсе; в rockchip-флоу колонка всё равно проходит
  usbplug-подключение (флаг известен только команде, не connect'у) —
  лишний MaskROM-цикл осознанно принят за унификацию флоу. Крайний
  случай (например, битый каталог); с
  подкомандой `backup` флаг несовместим и отвергается с ошибкой;
- колонка вошла без персоны лоадера (MaskROM напрямую, живой usbplug от
  прошлого прогона, нечитаемый серийник 330d) → серийник неизвестен, и
  `bring_up` **отказывается работать** с такой персоной: путь выбрать
  нельзя (ни кеш бэкапа, ни сценарий первого поколения), инструмент
  просит перезапустить колонку в режим лоадера и ждёт именно 330d
  (`refuse_unknown_identity` в session.rs);
- старые раскладки (плоский `backup/*.img`, `backup/<серийник>/` с
  SUCCESS.txt/SHA256SUMS, amlogic без `backup.json`) новыми версиями
  не читаются — см. выше, бэкап переснимается.

## adbd

Оверлейный `adbd` собирается герметично в контейнере (Debian bullseye,
кросс-тулчейн, стоковый ABI glibc ≤ 2.33 / libcrypto 1.1):

```sh
docker build -t capsula-adbd docker/adbd
docker run --rm -v docker/adbd:/work capsula-adbd /work/build.sh
```

## Релизы

Тег `v*` запускает `.github/workflows/release.yml`: сборка adbd в
Docker → матрица из 5 платформ → публикация GitHub Release.

- В Windows-архив вкладываются `RockchipUSBDriver.zip` (вендорский
  драйвер Rockusb для официальных утилит) и `zadig-2.9.exe` (перевод
  платы на WinUSB для capsula-jb). Оба пинуются SHA256 в env
  воркфлоу: при обновлении upstream обновляйте пин, при изменении
  суммы сборка падает, а не катит непроверенный бинарник.
- В каждый архив кладутся `resources/packaging/QUICKSTART.txt`,
  `resources/packaging/AGENTS.md` (инструкция для агентов по прошивке)
  и, для Windows, `resources/packaging/windows-DRIVER-SETUP.txt`.
- Изменения упаковки проверяйте локально: `TARGET=... ARCHIVE=...
  TAG=vX.Y.Z bash .github/scripts/package.sh` после сборки.
